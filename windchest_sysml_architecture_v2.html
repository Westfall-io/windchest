System Overview

Purpose

Windchest is a containerized application designed to collect workflow outputs, perform verification checks, and store artifacts in distributed object storage. It operates as part of a larger pipeline orchestrated by the Windrunner master workflow.

Key Capabilities

🔐 Authentication

Integrates with Keycloak OIDC for secure API access to Windstorm and MinIO services

📂 File Discovery

Automatically detects changed files from Git repositories using GitPython

✅ Verification

Validates outputs using JUnit-based file checking mechanisms

☁️ Storage

Uploads verified artifacts to MinIO S3-compatible object storage with configurable retention

🔄 Orchestration

Updates execution status and triggers dependent workflow tasks via Windstorm API

🐳 Containerized

Fully containerized deployment with automated CI/CD via GitHub Actions

Scaling and High Availability

Current Deployment Model

The current deployment model runs Windchest as a single-instance job-based container triggered by workflow events. Each execution is ephemeral and processes a specific action payload.

Scaling Considerations

  • Horizontal Scaling: Multiple instances can run concurrently for different workflow executions
  • State Management: All state is externalized to Windstorm API and MinIO - containers are stateless
  • Volume Access: Persistent volumes should support ReadWriteMany if running multiple concurrent instances
  • Resource Limits: Configure appropriate CPU and memory limits based on expected file sizes and verification complexity

Monitoring and Observability

📊 Metrics

  • Execution time (captured in code)
  • File count processed

  • Container resource utilization

📝 Logging

  • Standard output (print statements)
  • Container logs (Kubernetes)
  • Authentication events
  • Error conditions

🔍 Tracing

  • Thread execution ID tracking
  • Status updates to Windstorm
  • Workflow correlation
  • Dependency chain visibility

⚠️ Alerting

  • Authentication failures
  • Verification errors
  • Upload failures
  • Volume mount issues

Disaster Recovery

Backup Strategy

Configuration: Version controlled in Git

Secrets: Backed up via secret management solution

Artifacts: MinIO with configurable retention (default 7 days)

State: Externalized to Windstorm API (no local state)

Recovery Procedures

Container Failure: Kubernetes auto-restart or manual redeployment

Volume Loss: Re-execute workflow from source

Service Outage: Retry logic in workflow orchestration

Data Loss: Re-run verification from Git source of truth

System Interfaces

External Service Interfaces

MinIO S3 Storage Interface

Interface: MinIO S3-Compatible Storage
Protocol: HTTP/HTTPS with S3 API
Endpoint: storage-minio.artifacts:9000
Authentication: Access Key ID + Secret Access Key

Operations:
  - login_minio() -> MinIOClient
    * Establishes authenticated session
    * Returns client object for subsequent operations
    
  - create_bucket(client, action, thread_name, name, tmp_location)
    * Creates storage bucket if not exists
    * Uploads files from tmp_location
    * Applies retention policy from MINIORETENTIONDAYS
    * Tags artifacts with thread_name and action metadata

Data Formats:
  - Input: Files from /tmp/digitalforge
  - Output: S3 objects with metadata tags
  - Retention: Configurable (default 7 days)

Windstorm API Interface

Interface: Windstorm Workflow Orchestration API
Protocol: HTTP/HTTPS REST
Endpoint: windstorm-api-service.windstorm:8000
Authentication: OAuth2 Bearer Token (via Keycloak)

Operations:
  - login_windstorm_api() -> AuthToken
    * Authenticates using OIDC client credentials
    * Returns bearer token for API requests
    
  - update_thread_status(token, thread_execution_id, status) -> thread_name
    * Updates execution status (e.g., 'windchest_1', 'windchest_2')
    * Returns thread name for correlation
    
  - update_verification(token, verifications_id, error)
    * Updates verification result status
    * Sends boolean error flag
    
  - find_dependent_tasks_by_id(token, action) -> Dict | None
    * Queries for downstream dependent tasks
    * Returns action dict if dependents exist
    
  - execute_dependent_thread(token, action, thread_name)
    * Triggers execution of dependent workflow threads
    * Propagates thread context

Data Formats:
  - Request: JSON payloads
  - Response: JSON objects
  - Authentication: JWT Bearer Token

Git Repository Interface

Interface: Git Version Control System
Protocol: HTTPS / SSH
Client: GitPython 3.1.37

Operations:
  - git_configure() -> List[File]
    * Discovers changed files in repository
    * Returns list of file paths
    * Uses GitPython for repository interaction

Data Formats:
  - Output: List of file paths (strings)
  - Access: Read-only repository access
  - Protocol: Git protocol (HTTPS or SSH)

Keycloak OIDC Interface

Interface: Keycloak Identity and Access Management
Protocol: OAuth 2.0 / OpenID Connect
Endpoint: https://keycloak.digitalforge.app
Realm: test (configurable)

Operations:
  - OAuth2 Token Endpoint
    * Client Credentials Grant
    * Returns access_token, refresh_token
    * Token used for Windstorm API authentication

Configuration:
  - KEYCLOAKHOST: https://keycloak.digitalforge.app
  - KEYCLOAKREALM: test
  - WINDSTORMAPICLIENT: client_id (from secrets)
  - WINDSTORMAPISECRET: client_secret (from secrets)

Data Formats:
  - Request: application/x-www-form-urlencoded
  - Response: JSON with access tokens
  - Token Type: JWT Bearer Token

Implementation Notes

Architecture Highlights

  • Stateless Design: All persistent state externalized to Windstorm API and MinIO
  • Event-Driven: Triggered by workflow events, executes single action, exits
  • Modular: Clear separation between authentication, discovery, verification, storage, and orchestration
  • Security-First: OIDC authentication, secret management, signed container images
  • Cloud-Native: Kubernetes-ready with ConfigMaps, Secrets, and PersistentVolumes

Known Dependencies

  • The windbinder package is referenced but not included in the repository
  • Implementation details of MinIO, Windstorm, Git, and JUnit operations are in external package
  • Actual Kubernetes manifests are not in repository - examples provided here are illustrative
  • Volume must be pre-mounted at /mnt/vol or workflow will fail

Future Enhancements

  • Add structured logging (JSON format) for better observability
  • Implement retry logic with exponential backoff for transient failures
  • Add Prometheus metrics export for monitoring
  • Implement distributed tracing (OpenTelemetry)
  • Support for parallel file processing
  • Enhanced error reporting and alerting
  • Support for multiple storage backends beyond MinIO
  • Webhook notifications for workflow completion
